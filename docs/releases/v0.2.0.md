# GuardBench v0.2.0 (milestone 3, pilot-scale)

**This is a benchmark under construction, not a result.** No model or real code reviewer has been run
on it, no hypothesis (H1, H2, H3) has a verdict, and any run on the current held-out split (100 items,
below the pre-registered target of 150) would be a pilot.

## What is in it

- 20 small Python apps; 130 validated defect/clean-twin pairs: 30 public dev (6 per class) and 100 held
  out in a private repo (20 per class). Manifest hash of the held-out items in `prereg/split.sha256`.
- The original 12 apps are unchanged since `prereg-v2`; apps 13 to 20 were added in new directories
  (amendment set 3, tag `prereg-v3`).
- `guardbench report` and `docs/RESULTS.md`: random, hunk-all and a toy script with Wilson intervals.
- A command-reviewer contract, a streaming 1 MiB output cap, and `examples/toy_reviewer.py`.
- No API keys and no model calls anywhere in the repository.

## Limits, restated

- Defects are **synthetic**, written by one AI agent; they have planted-bug style artifacts. A toy
  40-line script finds 52% of held-out defects (all removed-validation, almost all fail-open, none of
  secret-leakage or off-by-one), so a real reviewer's recall must be read against that.
- **Small n**: 100 held-out pairs, 20 per class; intervals are wide.
- Noise is cosmetic and, for the new apps, reproducible from the public generator.
- Held-out apps' public READMEs and tests name the rule each defect breaks.
- `validate` executes code and is **not a sandbox**; a `command` reviewer is not sandboxed at all.
- Self-reviewed by the author agent; no independent human review.
- Developed on Windows; CI is Linux (Python 3.10, 3.12).
